# Audit and remediation plan — 2026-07-24

Five independent read-only audits plus two measurement experiments, run after a
session where wake-phrase enrollment was debugged for hours inside assumptions that
were never checked. Every item below carries the evidence that produced it and the
command that proves it fixed. Items are grouped by consequence, not by effort.

Ground rules for implementation:

- Nothing in here publishes anything. Do not push, do not make the repo public, do
  not cut a release, do not touch the Homebrew tap. Prepare, don't ship.
- If an item's evidence turns out to be wrong when you look at the code, stop and
  say so rather than implementing around it. Two findings in this audit were
  themselves corrections of earlier confident claims.
- Every behavioural change lands with one runnable check. "Builds clean" is not a
  check.

---

## P0 — would harm users or mislead them if published

### P0.1 The app breaks a privacy promise it makes on screen

`SettingsWindowController.swift:133` tells the user "Nothing is recorded, nothing is
stored, and nothing is sent anywhere." `README.md:22` says "Nothing is recorded.
Nothing is uploaded." But `WakePhraseEnrollmentWindowController.swift:319` calls
`EnrollmentDiagnostics.record(...)` unconditionally on every enrollment attempt, and
`EnrollmentDiagnostics.swift` writes `~/Library/Application Support/HeyCodex/enrollment.log`
containing the phrase the user typed, the tokens the model decoded from their voice,
per-threshold firing results and clip durations. There is no opt-out and no UI
mentioning it. The privacy claim sits directly above the button that triggers the
writing.

Fix: make the log genuinely opt-in, gated the same way the audio already is
(`EnrollmentDiagnostics.keepsAudio`, a marker file no UI exposes). A user who has not
created that marker file must produce no on-disk artifact from enrollment beyond the
keyword file and settings they explicitly chose. Keep the diagnostics capability —
it is what made tonight's root-causing possible — but it must be off by default.

Verify: with no marker file present, run an enrollment and confirm `enrollment.log`
does not appear. With the marker file, confirm it does.

### P0.2 Every fresh install runs at a keyword boost the code itself calls unsafe

`Settings.swift:82` defaults `wakeKeywordsScore` to `2.0`, and that is what builds
the live engine at `AppController.swift:290`. `KeywordTuning.swift:19` sets the
calibrated value to `1.5`, and the comment two lines above warns that "values above
roughly 2 start surfacing keywords on weak acoustic evidence, which reads to a user
as random triggering." The bundled `Models/keywords.txt` carries no per-line score,
so nothing overrides the global. The 1.5 only takes effect after a user enrolls a
custom phrase. `AppController.resetWakeSensitivity` never touches the score, so
there is no in-app path back.

Fix: one source of truth. `Settings.default.wakeKeywordsScore` must be
`KeywordTuning.score`, not a second hardcoded literal.

Verify: a test asserting `Settings.default.wakeKeywordsScore == KeywordTuning.score`,
so the two can never drift apart again silently.

### P0.3 CI has failed on every push, all day, on a self-contradicting check

`scripts/fetch-sherpa.sh:118` greps `nm` output for `_OrtGetApiBase` and finds it
(the log prints `0000000000004b4c T _OrtGetApiBase`). Line 119 then re-greps the same
output with `grep -qE " [TtWw] _OrtGetApiBase"` and fails, aborting the build. Every
run on `main`, `v0.1.1` and the working branch is red. An automated check was
reporting a problem all session and nobody read it.

Fix: make the gate match the format `nm` actually emits on the runner. The two greps
one line apart must agree by construction — derive the strict check from the same
output the loose one prints, or drop the loose one.

Verify: `scripts/fetch-sherpa.sh` completes locally, and the next CI run on this
branch is green. Do not weaken the check into a no-op: it exists to catch a genuinely
broken merged archive.

### P0.4 Release tooling would regress a fix that is already live

`scripts/make-release.sh:51-58` generates cask text instructing
`brew install --cask --no-quarantine`. That flag was removed in Homebrew 6 (local
`brew --version` is 6.0.12; the flag errors). The deployed cask in
`cyburke/homebrew-tap` was hand-patched to use a `postflight` block that strips
`com.apple.quarantine` instead. Running the release script as documented would
regenerate the broken instruction and drop the working fix.

Fix: the generator must emit the postflight form that is actually deployed, and the
version it writes must come from `scripts/Info.plist` rather than an argument nobody
cross-checks. (`Info.plist` says 0.1.2; the published cask says 0.1.1.)

Verify: run the script with a dummy version into a temp dir and diff its output
against the live cask, confirming the only difference is version and sha256.

## P1 — real defects that shape whether the product works

### P1.1 Quiet recordings silently break enrollment for everyone

Measured on this Mac: the user's three real enrollment takes are RMS 0.005–0.009
against the model's own reference audio at 0.047, i.e. 5.1× to 9.1× quieter. A
synthesized "hey codex" that fires at *every* threshold at normal level produces
**zero hits at every threshold** when scaled down to RMS 0.006. So a phrase the model
handles perfectly is silenced by level alone, and today the user is told to check
their microphone or say it differently.

Important negative result from the same experiment: normalizing gain does **not**
rescue "hey xena" — RMS-matched, peak-normalized, thresholds down to 0.02 and boost
at 3.0 all produced no detection. Gain is a real and separate problem. Do not sell it
as a fix for unspottable phrases.

Also measured: RMS-matching alone was not sufficient for one synthesized voice whose
crest factor differed, so peak headroom matters, not just RMS.

Fix: normalize capture level before fire-testing during enrollment, and tell the user
when their input is far below a workable level, in the recorder rather than after
three takes. Choose the normalization target from the measurements above, and state
the chosen numbers in a comment.

Verify: a selftest probe that takes the three saved takes (or synthesized stand-ins),
scales one to RMS 0.006, and asserts that a known-good phrase still enrolls after
normalization while a synthesized ordinary sentence still does not fire. Extend
`swift run hey-codex-selftest replay-enrollment` rather than inventing a new harness.

### P1.2 The failure message blames the user's microphone for a phrase that cannot work

`WakePhraseEnrollmentWindowController.swift:328-330` says "None of the three
recordings triggered the phrase. Check the right microphone is selected, then try
again." The app already knows from `WakePhraseFitness` moments earlier when a phrase
cannot be spotted at any threshold. Sending that user to audio settings is a dead end.

Fix: branch on what the app already knows. If fitness said `.cannotSpot`, say the
phrase is the problem and suggest trying another. If fitness cleared it, then
microphone and delivery are fair advice — and if P1.1 detected a low input level,
say that specifically.

Verify: covered by the fitness/replay probe plus a read of the three copy paths.

### P1.3 The README promises something the model cannot deliver

`README.md:68` — "Genuinely anything. ... Your dog's name." Measured: `hey xena`,
`hey chatgpt` and `hey buddy` never fire at any threshold, because the model's
500-piece vocabulary cannot represent some words (no word-initial piece begins with
X, so "xena" encodes with a soundless boundary token). `WakePhraseFitness.swift`
documents this in its own header. The in-app check is honest; the README contradicts
it one screen away.

Fix: say what is true — most short phrases work, the app tests the phrase as you type
and tells you when one looks unlikely. Do not enumerate blocked phrases as a
blacklist; the check is empirical and per-voice.

### P1.4 `bpe.model` versus `bpe.vocab`: settle it with a measurement

`KeywordTuning.bpeVocabName` is `"bpe.model"` (`KeywordTuning.swift:36`), and
`WakeWordEngine.swift:47-49` looks for that file to decide whether to pass
`modeling_unit: "bpe"` or fall back to `"cjkchar"`. The file is not in the bundle
allowlist, confirmed absent from `dist/HeyCodex.app` — so every shipped build runs
with `cjkchar`. Separately, we now generate `bpe.vocab` for our own tokenizer, which
is a different file in a different format.

Two claims in the tree are wrong regardless: `scripts/bundle-app.sh:38` says these
files are "not read at runtime" when the engine does check for one, and
`WakeWordEngine.swift:24-26` says that with these set "keywords may be written as
plain text and sherpa tokenises them" — false for this app, which pre-tokenizes every
keyword before sherpa sees it.

Note a correction to an earlier claim made during this session: these fields *do*
exist and *are* passed through — they live on `SherpaOnnxOnlineModelConfig`
(`c-api.h:232-269`), which is embedded in the keyword spotter's config. The earlier
statement that they "do not exist in the KWS config" was wrong.

Fix, in this order: (1) measure whether detection differs at all between
`modeling_unit: "bpe"` with a real vocab present and `"cjkchar"`, using the existing
`HEYCODEX_KWS_DEBUG=1` path and a threshold sweep on real audio; (2) then either wire
it correctly or delete the plumbing, based on what the measurement shows; (3) fix both
false comments either way. Do not delete first and assume.

### P1.5 Diagnostics that cannot report their own failure

`EnrollmentDiagnostics.swift` wraps every write in `try?` — directory creation, file
handle, audio write. A failed write is indistinguishable from working. This is the one
component whose entire purpose is leaving a record. Same pattern hides a missing model
file in `WakeWordEngine`'s vocab lookup, and `guard let engine = try? WakeWordEngine(...)`
collapses every distinct `missingModelFile` case into one generic branch.

Fix: surface the failure where a human will see it. The diagnostics writer should
report that it could not write; the engine construction sites should preserve which
file was missing.

## P2 — inherited residue to remove

Confirmed dead by grep across `Sources`, `Tests` and `scripts`. All of it is
`littlemelon77/hey-claude` heritage — that app routed to editors and CLIs, had an
island/mascot UI, and had push-to-talk. Hey Codex presses one hotkey.

- **Push-to-talk, entirely inert**: `PushToTalkKey.swift` (72 lines, only
  self-references), `ManualCaptureFlag.swift` (40 lines, never instantiated), and
  `Settings.pushToTalkKey` (`Settings.swift:54`) which is persisted to every user's
  `settings.json` for a feature that cannot fire. No `CGEventTap` exists anywhere in
  the app. `PushToTalkKey.swift:52` cites a `decodeEdge` function that does not exist.
- **Never instantiated**: `AppStateMachine` (`App/AppState.swift:29`),
  `IdeLockfileReader` (`Detection/IdeLockfileReader.swift:10`), `RecentActions`
  (`App/RecentActions.swift:6`).
- **UI concepts with no screen**: `Island/IslandModel.swift` (79 lines, unreferenced
  outside its directory), the `Mascot` layer, and `Island/MascotGrid.swift` whose
  comment claims it is "Rendered by MascotView" — no such type exists.
- **Editor-routing detection** (`Detection/EditorAvailability.swift` unused methods)
  now only serves selftest probes for a capability the product does not have.
- **Small unused surface**: `LaunchTarget.displayLabel`, `LaunchFailure.settingsActionLabel`,
  `IslandModel.onboardingPlaceholder`, and the never-overridden `modelingUnit` /
  `bpeVocabFile` parameters on `WakeWordEngine.init` (see P1.4 first).

By directory, types referenced by the app: App 0/4, Detection 0/3, Island 0/2,
Mascot 0/3, Routing 0/1, Transcribe 0/1, Actions 1/8, Commands 1/5 — out of 5,726
lines in the kit. Some of that is reached indirectly (`VoiceActivityDetector` is
genuinely used by capture; `WakePrefixStripper` by the session), so **delete by
verified reference, not by directory**.

Also: two files cite "internal design notes" as the authority for a value
(`WakeWordEngine.swift:18`, `IdeLockfileReader.swift:9`). That document is not in the
repo. Either state the real justification or remove the citation — pointing at
evidence that does not exist is worse than saying "unmeasured".

Verify for all of P2: `swift build`, full `swift test`, `swift run hey-codex-selftest all`,
and a bundled-app smoke test. Removal must not change the app's behaviour at all.

## Deliberately NOT doing, with the data

**Do not switch to the phoneme KWS model** (`sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`).
It is the obvious fix for "the vocabulary cannot spell X", and in principle it is:
that model maps `HEY XENA` and `HEY ZENA` to identical phonemes
(`HH EY1 Z IY1 N AH0`), so the X-versus-Z problem does not exist there at all.

It was rejected twice, and the first rejection was wrong in a way worth recording.
That test swept the three real recordings at their original level and reported 0/3,
before anyone knew that level alone silences detection. Re-run with the same gain
normalization the app now applies (targetRMS 0.047, peakCeiling 0.5), the bare word
"zena" went from 0/3 to **2/3** — so the original test was partly measuring loudness,
not the model, and that specific claim did not hold.

What survives the corrected test:

- "Hey Xena" and "Hey Zena" fire **0/3 normalized and 0/3 raw**, at every threshold
  0.25-0.08 and at scores 1.0 and 1.5. Pushed to score 3.0 they reach only take-3.
  The two-word phrase is not a loudness artifact.
- Bare "zena" peaks at **2/3** (take-1 never fires; it is the take that stays furthest
  under target RMS because the peak ceiling caps its gain). The BPE model already in
  the app does **3/3 on that word at the strictest threshold**, so the alternative
  loses to what ships today.
- The lexicon gap is a product blocker, not a tuning problem: "CODEX" is absent from
  `en.phone`, and `text2token` prints a warning, **exits 0, and writes an empty keyword
  file**. A release pipeline checking exit status would ship an app with no wake word.
  Every default user would need a hand-authored pronunciation, and so would every
  invented name a user types, because the pipeline has no grapheme-to-phoneme fallback.
- No false-alarm advantage to offset any of it: 5 ordinary sentences produced 0 hits
  on both models. (A sentence containing the literal word "Zena" fired, correctly.)

Environment note for anyone re-running this: pin `sherpa-onnx==1.13.3`. Version 1.13.4
silently detects nothing on Apple Silicon (see below), and the phoneme model's own
bundled `test_wavs` are the sanity check that proves the harness works before any
negative result is believed.

Open for a future version: a phoneme model plus a real G2P fallback would allow
genuinely arbitrary wake phrases. That is a feature, not a fix for this bug.

**Do not upgrade sherpa-onnx to v1.13.4.** Its bundled ONNX Runtime 1.27.0 has an
Apple Silicon SME convolution bug that makes `KeywordSpotter` detect **nothing**,
silently — reproduced on this Mac against the model's own test files, and reported
independently upstream as k2-fsa/sherpa-onnx#3791 (fixed in ORT 1.27.1). Being pinned
two releases behind is currently protecting us. Record this in `fetch-sherpa.sh` next
to the pin so nobody "modernises" it. Revisit when a release ships ORT ≥ 1.27.1.

## Open questions, and the experiment that would answer each

1. **Why does "hey xena" fail?** Gain is ruled out. Vocabulary is the leading
   explanation but the specific mechanism — whether the token spelling
   `▁HE Y ▁ X EN A` is wrong for how anyone pronounces it, or whether the model's
   acoustic model simply cannot resolve that sequence — is untested. Experiment:
   arm several hand-written alternative encodings of the same pronunciation and sweep
   them against the three saved takes.
2. **Does `modeling_unit` change anything?** See P1.4 — one measurement settles it.
3. **What is a defensible value for `score` and `numTrailingBlanks`?** Both are
   currently GUESSED. `probeTuning` sweeps them but only prints to a terminal;
   nothing is committed. Experiment: run the sweep on real recordings and commit the
   output so the number has a source.

## Publish checklist, for whenever the repo goes public

Not part of this remediation, listed so it is not rediscovered later: the repo is
private and its only release is a draft, so the README install command, the shields
badges, and `UpdateCheck`'s releases API all 404 for everyone but the owner. The live
cask points at a `v0.1.1` asset that does not exist while `Info.plist` says 0.1.2.
`UpdateCheck` degrades honestly (reports "could not read the latest version" rather
than claiming up to date), so this is not a crash risk — it just cannot work until
the repo is public and a real release exists.
