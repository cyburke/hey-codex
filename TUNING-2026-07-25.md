# Wake-word tuning grid: `score` and `numTrailingBlanks` — 2026-07-25

Answers AUDIT-2026-07-24.md, "Open questions" item 3: `KeywordTuning.score` and
`KeywordTuning.numTrailingBlanks` were GUESSED (1.5 and 2, against library
defaults of 1.0 and 1), with no committed evidence. This file is that evidence.

Regenerate the grid with:

```
swift run hey-codex-selftest tuning
```

Add `HEYCODEX_TUNING_DIAG=1` in the environment to also print which specific
clip/keyword pair produced each false alarm. The command prints to stdout
only - it does not write this file - so updating this file after a rerun is
a manual copy of the new output.

Run on: 2026-07-25, this Mac, `sherpa-onnx` pinned per
`scripts/fetch-sherpa.sh` (1.13.3 — see AUDIT-2026-07-24.md re: the 1.13.4
Apple Silicon SME bug).

## Method

- **Grid axes**: `score` in {1.0, 1.25, 1.5, 1.75, 2.0} x `numTrailingBlanks`
  in {1, 2, 3}, at the shipped `threshold` of 0.25 (not swept — P0.2 already
  pins the default install to it, and a three-axis grid stops being readable).
- **Gain normalization**: every clip, synthetic and real, goes through
  `AudioSamples.normalized(_:targetRMS: 0.047, peakCeiling: 0.5)` before
  testing — the same call the app now makes before enrollment fitness checks
  — so this measures runtime behaviour, not raw `say` output levels.
- **One keyword armed per engine**, matching production: `AppController.swift`
  and `WakePhraseEnrollmentWindowController.swift` both build `keywordsFile`
  from exactly one active phrase (the bundled default, or whichever phrase the
  user enrolled), never several at once. The first version of this
  measurement armed all candidate phrases plus the model's own reference
  keywords together in a single engine; every cell then "false-alarmed" on
  the same clip, "hey there how are you" (Samantha) — which turned out to be
  the model's own reference keyword `FOR EVER` firing, not any phrase a real
  install would ever have armed alongside it. Splitting to one engine per
  keyword removed that cross-keyword contamination and is also the more
  honest measurement of what ships.
- **Positives evaluated with `WakeWordEngine.detects(in:)`**, which pads a
  full second of trailing silence to reliably flush the chunk-16 zipformer's
  last chunk (see the comment on `detects(in:)`). This matches production: the
  app's capture window keeps recording past the wake word until VAD sees a
  pause, so there is always ample trailing silence by the time detection
  runs.
- **False alarms evaluated by streaming** (`WakeWordEngine.feed()`,
  ~100 ms/frame, matching the live mic loop) over the negative clip's own
  audio with nothing appended — no artificial trailing pause. `numTrailingBlanks`
  exists specifically to suppress a keyword fragment firing mid-sentence
  while more speech keeps coming; a padded one-shot test cannot exercise that
  at all (an earlier version of this grid, using `detects(in:)` for both
  sides, showed literally zero effect from `numTrailingBlanks` at 1/2/3,
  because the 1s pad trivially satisfies any of the three).

## Corpus

**Positives** (32 total: 30 synthetic across 6 candidate phrases, +3
reference-keyword sanity clips scored separately, not part of the false-alarm
surface):

- `hey codex` (the shipped default), `hey jarvis`, `hey computer`, `ok codex`,
  `wake up codex`, `hey samantha` — each synthesized via `/usr/bin/say` in 5
  voices: **Samantha, Alex, Daniel, Karen, Fred**. (Alex is not installed on
  every macOS version; Fred substitutes for it here as a second US English
  voice distinct from Samantha — both were confirmed present on this Mac
  before the run.)
- The model's own reference clips, `Models/sherpa-onnx-kws-zipformer-gigaspeech-3.3M-2024-01-01/test_wavs/{0,1}.wav`,
  armed with the model authors' own shipped keyword lines
  (`test_wavs/test_keywords.txt`: `LIGHT UP`, `LOVELY CHILD`, `FOR EVER`) —
  real recorded speech, not synthetic, used as a positive-detection
  regression control only. No install ever arms these in production, so they
  are reported in their own `ref` column and excluded from the false-alarm
  count.

**Negatives** (43 total, each tested against every one of the 6 candidate
phrases' own single-keyword engine — 258 checks per grid cell):

- 8 ordinary sentences, synthesized in the same 5 voices: "hey there how are
  you", "I put it in a bag", "let me check the code for you", "the weather
  today is warm", "can you help me with this later", "I think we should go
  home now", "that sounds like a great idea", "please turn off the lights
  before you leave". Several are deliberate near-misses ("hey there…" against
  "hey codex"/"hey computer"; "let me check the *code*…" against `codex`).
- The three real human recordings at
  `~/Library/Application Support/HeyCodex/enrollment-audio/take-{1,2,3}.wav`.
  **These are recordings of "Hey Xena," a phrase this model cannot spot at
  all** (AUDIT-2026-07-24.md, "Deliberately NOT doing"), captured on a distant
  monitor mic at RMS 0.005–0.009 — 5–9x below the KWS model's own reference
  level of 0.047. They are unusable as positive evidence for anything in this
  grid, since they say the wrong words entirely. They are folded in here only
  as the hardest available negative: real, quiet, off-keyword human speech —
  if gain normalization were going to manufacture a false trigger out of
  noise-floor artifacts, this is where it would show up. It did not.

## Where the peak ceiling capped normalization short of target RMS (0.047)

```
test_wavs/1.wav (LOVELY CHILD)                          preRMS=0.0306  postRMS=0.0361
test_wavs/1.wav (FOR EVER)                               preRMS=0.0306  postRMS=0.0361
take-1.wav (real "hey xena", quiet mic, stress-only)     preRMS=0.0092  postRMS=0.0316
take-3.wav (real "hey xena", quiet mic, stress-only)     preRMS=0.0062  postRMS=0.0435
```

`take-1.wav` and `take-3.wav` have high crest factors (a few loud peaks over
an otherwise quiet recording), so `peakCeiling` held their gain well short of
target RMS even after boosting — consistent with the audit's note that
RMS-matching alone is not sufficient for every voice. `test_wavs/1.wav` was
capped less severely (0.0306 → 0.0361 against a 0.047 target). `take-2.wav`
reached target and is not listed.

Every cell reached **zero false alarms** — including against the real quiet
"hey xena" takes. `numTrailingBlanks` had no effect at score 1.0/1.25 and a
small effect (+1 positive at blanks=3) at score 1.5/1.75/2.0. Positive
detection is **not monotonic in score**: it peaks at 1.25 and *drops* as score
climbs to 1.5–2.0. This is counterintuitive — a higher keyword-path boost
should make detection easier, not harder — but it is real and reproducible
across repeated runs. The likely mechanism: `maxActivePaths` is 4 (library
default, out of scope here), and a larger boost changes which hypotheses
survive that beam-width cut, sometimes crowding out the path that would have
matched the true phrase. This is worth a dedicated `maxActivePaths` sweep in
a future round, but that lever is explicitly out of scope for this task.

The shipped default phrase, `hey codex`, hit **5/5** at the winning cell —
every voice, every time. `hey samantha` is the weak phrase in this corpus
(2/5), most likely because "samantha" gives the 3.3M model fewer distinctive
syllables to anchor on; it is not the phrase this repo ships and its weakness
does not change the recommendation below. `Fred` was the hardest voice across
several phrases.

## Winner

**score = 1.25, numTrailingBlanks = 1** — 24/30 positives (80.0%), 0/258 false
alarms, reference-keyword regression clean (3/3 in every cell). This
maximizes positive detection among the zero-false-alarm cells; the tie
`(1.25, blanks=1/2/3)` (all 24/30) broke to the lowest `numTrailingBlanks`,
per the stated preference (lower score relies less on the beam boost; lower
blanks means less latency before the wake fires).

**This differs from the previously shipped values (score=1.5,
numTrailingBlanks=2).** The measured score is lower — the guess had
over-corrected in the boost direction: 1.5 measures out to *worse* positive
detection than 1.25 in this corpus (22-23/30 vs 1.25's 24/30), with an
identical zero false alarms either way, so there was no upside to the extra
boost. The measured `numTrailingBlanks` is lower too — 1 rather than 2 —
which is a straightforward latency win with no measured false-alarm cost in
this corpus.

## What this does and does not establish

This is a **synthetic-speech-dominated** measurement: 30 of 32 positives and
40 of 43 negatives are `say`-generated voices. Multiple voices (5, not 1) were
used deliberately, because a single-voice measurement is exactly the mistake
this repo already made once (see AUDIT-2026-07-24.md's "zena" re-test, which
initially used one voice and drew a conclusion that partly did not hold). But
synthetic speech remains a proxy for human speech: it lacks real prosody
variance, background noise, microphone coloration, and the full range of
accents and speaking rates. It does NOT establish that these settings are
optimal for arbitrary real human voices, only that they are the best
measured tradeoff across this synthetic + limited-real-audio corpus at the
shipped threshold.

The three real recordings used here are of the WRONG phrase ("hey xena", not
any of the six candidate phrases) and were used exclusively as a hard,
quiet, real-microphone **negative** stress case — never as positive evidence.
No real human recording of any of the six candidate phrases exists in this
repo at time of writing; the P1.1 quiet-mic finding remains a separate,
already-documented risk that this tuning grid does not re-litigate.

## What proved wrong along the way

The first version of this grid armed one engine with every candidate phrase
plus the model's reference keywords all together, mirroring the earlier
"tuning" probe's structure. Every cell false-alarmed on "hey there how are
you" (Samantha) — turned out to be the reference keyword `FOR EVER`, not any
phrase a real install would ship alongside a wake word. That measurement
would have produced "no winner: every cell has a false alarm," which is both
wrong and would have blocked this task. Splitting to one keyword per engine
(matching what `AppController.swift` actually builds) fixed it and is the
version this file reports.

Testing `numTrailingBlanks` via the padded `detects(in:)` call (positives'
usual 1-second silence tail) also produced zero measurable effect across
1/2/3 in an early version — because a full second of silence trivially
satisfies any of those three. Moving false-alarm evaluation to streaming
`feed()` over the negative clip's own audio, with no artificial pad, was
necessary to make the parameter show any effect at all.
